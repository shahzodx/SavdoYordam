# Реализованные пользовательские сценарии

1. **Начало:** выбор языка → аккаунт email/password → название магазина → пустой каталог → добавить товар. Для повторного создания магазина используется сохранённый клиентский UUID. Нет тестовых кодов и скрытой dev-авторизации.
2. **Продажа:** поиск по имени/SKU → добавить позицию (для кг/литра указать точное количество) → корзина → клиент при необходимости → фактически оплаченная сумма → наличные/карта → проверка оставшегося долга → подтверждение. Сервер проверяет цену, остаток, tenant и сумму. Успех обновляет историю и Dashboard.
3. **Сбой сети:** команда записана локально → статус ожидания → настройки синхронизации → повтор того же запроса → подтверждение или явный конфликт. Pending не равен завершённой продаже.
4. **Долг:** клиент → история покупок → продажа с долгом → сумма погашения → дополнительное подтверждение клиента, суммы и будущего остатка → запись платежа. Долг обновляется отдельной записью ledger.
5. **Возврат:** история → продажа → полный возврат → причина и пояснение возврата денег → серверная обратная операция. Частичного возврата нет.
6. **Товар:** каталог → товар → редактирование названия/SKU/цены/себестоимости/минимума → проверка версии. Исторические строки продаж сохраняют прежние значения.
7. **Остатки:** каталог → товар → изменение количества со знаком и причиной → проверка версии → движение склада. Отрицательный итог запрещён.
8. **Расход:** быстрая кнопка или отчёты → расходы → категория/сумма/дата/способ/описание. Закупку запасов не следует записывать здесь как себестоимость проданных товаров.
9. **Настройки:** язык, очередь, повторный вход, выход, помощь и информация о конфиденциальности. Выход блокируется при unresolved-командах; повторный вход доступен для истёкшей сессии.

Все каталоги без данных показывают empty state. DataView содержит загрузку, error и retry. При недоступности сервера доступны сохранённые ответы с баннером. Скрытие кнопок по роли пока не реализовано; окончательное разрешение всегда проверяется API.
