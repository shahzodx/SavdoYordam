# 2. ГЛАВНЫЕ ПРОДУКТОВЫЕ ПРИНЦИПЫ

Следуй этим принципам при принятии любых решений.

### 2.1. Simplicity First

Пользователь не должен задумываться, где находится нужная функция.

Убери лишние действия, экраны и настройки.

Каждый элемент интерфейса должен иметь конкретное назначение.

### 2.2. Speed First

Приложение должно быть оптимизировано для недорогих Android-смартфонов.

Целевые показатели, которые необходимо проверять на реальных устройствах:

- Быстрое открытие ключевых экранов.
- Мгновенная обратная связь на действия.
- Быстрый локальный поиск товаров.
- Плавная прокрутка длинных списков.
- Минимальная задержка при регистрации продажи.
- Отсутствие блокировки интерфейса при синхронизации.

Не заявляй точные показатели производительности без измерений.

### 2.3. Reliability First

Потеря или дублирование продаж недопустимы.

Финансовые операции должны быть транзакционными, проверяемыми и восстанавливаемыми.

### 2.4. Offline First

Приложение должно предоставлять полезные функции даже без интернета.

Однако безопасность многопользовательских офлайн-продаж важнее формального наличия офлайн-режима.

### 2.5. Design Excellence

Создай не просто красивое, а удобное приложение.

Продумай каждое состояние экрана:

- Empty
- Loading
- Success
- Error
- Offline
- Syncing
- Conflict
- Permission denied

### 2.6. Trust by Design

Пользователь должен понимать, что произошло с его деньгами, товарами и записями.

Система обязана показывать результат операции и позволять исправить ошибки с сохранением истории.

Это один из важнейших разделов.

Я хочу, чтобы SavdoYordam воспринимался как современный, тщательно разработанный продукт, а не стандартное приложение, собранное из готовых компонентов без дизайнерского замысла.

Ориентируйся на общие принципы лучших финансовых, операционных и продуктивных приложений:

- Визуальная ясность.
- Спокойная премиальная эстетика.
- Отличная типографика.
- Продуманная иерархия информации.
- Минимум визуального шума.
- Высокая читаемость цифр.
- Быстрые и предсказуемые взаимодействия.
- Небольшие приятные анимации.
- Последовательность всех компонентов.

Не копируй конкретные приложения, чужие интерфейсы или брендинг.

Создай собственный визуальный язык SavdoYordam.

Используй:

- Последовательную систему отступов.

Состояния не должны различаться только цветом.

# 15. OFFLINE-FIRST ARCHITECTURE

Продумай офлайн-режим как полноценную архитектурную часть.

Используй:

- SQLite + Drift для локальных данных.
- Очередь исходящих операций.
- Уникальные идентификаторы команд.
- Idempotency keys.
- Версионирование данных.
- Надёжные повторные отправки.
- Обработку конфликтов.
- Отображение статуса синхронизации.

## Принцип

Пользователь создаёт операцию.

Приложение сохраняет её локально в допустимом сценарии.

Операция получает уникальный идентификатор.

При наличии сети приложение отправляет её серверу.

Сервер проверяет права, данные и бизнес-правила.

PostgreSQL выполняет атомарную транзакцию.

Сервер подтверждает применение операции.

Локальная база отмечает запись как синхронизированную.

При повторной отправке сервер не должен проводить ту же продажу второй раз.

## Важное ограничение MVP

Полноценные офлайн-продажи допускаются только для одного активного устройства магазина, если система не реализует более строгий безопасный механизм согласования остатков.

Для нескольких устройств без интернета не обещай автоматическую бесконфликтную синхронизацию.

При спорных операциях показывай явный статус и требуй разрешения конфликта.

Отсутствие связи должно отображаться понятно.

Не показывай несинхронизированную продажу как окончательно подтверждённую сервером.

Не удаляй локальную очередь до получения достоверного подтверждения.

Подготовь тесты отключения сети, повторной отправки и восстановления после перезапуска.
